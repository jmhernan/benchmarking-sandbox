# Making bench_press verdicts statistically valid: a proposal

**Audience:** the bench_press maintainer(s).
**Scope:** statistics only: what the verdicts claim, when the claim holds, and how to make it hold.
**Basis:** bench_press at commit [`e21db31`](https://github.com/kevmoo/bench_press/tree/e21db31). Every number in §6 comes from [simulate.py](simulate.py) (seeded; runs in seconds with numpy and scipy).
**Status:** see [§0](#0-status-update-2026-10-25) for what has changed since: v0.4.2 implemented much of §7, there is a first measurement on real hardware, and the method has been validated in simulation. §1–§8 are unchanged, so their numbers still reproduce from `simulate.py` at `e21db31`.

## 0. Status update (2026-10-25)

### 0.1 What v0.4.2 (`5fd6396`) implemented from §7

PRs #81–#84 implemented the core of the proposal. All of it is opt-in: the defaults (`--processes 1`, `--threshold 0`) keep today's single-process interval and ±5% band.

| §7 suggestion | Status in v0.4.2 |
|---|---|

| 2. Process-level Fieller | ✅ When P > 1 the interval uses per-process means, with Welch df. It is paired (with covariance) when group variants share the same process launches. |
| 3. `--threshold δ` | ✅ Faster/Regression if the 95% interval clears 1+δ or 1/(1+δ); Equivalent if the **90%** interval lies inside (TOST at 5% per side); otherwise Inconclusive. It sits alongside the ±5% band. |
| 4. Diagnostics | ◐ `between_process_share` is reported, but not σ̂₁, σ̂₂ or k̂ (and see 0.4(b)). |

| 6. Design hints, multiple comparisons, adaptive stopping | ❌ Not yet. |

We checked the new code by porting it to Python and matching it **to 1e-9** against fixtures generated by bench_press itself: 493 Fieller cases, 104 t and normal quantiles, 408 delta-table verdicts at three thresholds, and `ProcessVarianceComponents`. The interval and verdict logic does what it says.

### 0.2 First measurement on real hardware

§8 called σ₂ on Dart AOT "the key unknown". This is a first answer, from **one benchmark on one machine**: an A/A pilot of a controlled sort workload, 40 processes × 16 trials of one AOT binary, Dart 3.13.7 on an Apple-silicon Mac.

| Quantity | Value |
|---|---|
| σ₁ (trial-to-trial within a process) | 1.51% [1.38, 1.64] |
| σ₂ (process to process) | 1.34% [0.98, 1.62]; 1.29% allowing for autocorrelated trials; **0.82%** after removing drift across the session |
| k̂ (how much a single-process interval understates the uncertainty) | 3.7 [2.8, 4.5] |
| Single process vs single process, same binary (780 pairs): printed 95% interval excludes 1 | **57%** (should be 5%) |
| Same pairs: verdict with `--threshold 0.03` | 4% "slower ≥ 3%", 71% Equivalent, 25% Inconclusive |
| Process-level Fieller, random 5 vs 5 / 10 vs 10 | excludes 1 in 5.4% / 5.1%; no false "≥ 3%" claims |

So σ₂ ≈ 1% is realistic, and the §6 scenarios at σ₂ = 0.5–1% are the relevant ones. Two features of the data matter for 0.4:
- **Correlated trials.** Successive trials within a process are correlated: median lag-1 correlation 0.25, and 0.46 after bias correction.
- **Session drift.** The first ~10 processes ran 2–4% faster than the rest, probably thermal.

The A/A, known-effect and same-binary runs of §5.2, on more benchmarks and on different days, are next.

### 0.3 Validation in simulation (contribution 3)

We ran a simulation harness through the Python port, with 4,000 replications per cell over P ∈ {2, 3, 5, 10, 20}, σ₂ ∈ {0–2%}, σ₁ ∈ {1, 3%} and θ ∈ {1.00–1.10}, plus robustness scenarios.
- **Coverage:** process-level Fieller covers **≥ 94.3% in every cell with P ≥ 3**, and 94.3–96.3% at P ≥ 5. At P = 3 it is conservative (up to 97.7%), because Welch's df is small.
- **Robustness:** coverage stays ≥ 94.4% at P ≥ 5 under t₃ noise, spikes, correlated trials, slow episodes, interleaved drift, unequal σ₂ between versions, bimodal process effects and a missing process.
- **Gate (δ = 3%):** at most 0.7% false "faster ≥ 3%" at θ = 1.02, and 97% power at θ = 1.05 with P = 10 (σ₁ = σ₂ = 1%).
- **Group mode:** the paired interval covers 94.5–95.5% and is 0.34–0.48× as wide as the unpaired one when variants share each process's effect.
- **20-benchmark suites:** zero false gate claims in every mix. The "detectable" label (interval excludes 1) gives about 1 false flag per all-null run, 0.06 with Benjamini–Hochberg.

The full results and acceptance criteria are in [`sandbox/output/a4/summary.md`](../../sandbox/output/a4/summary.md), reproducible with `python -m bench_stats.validate`.

### 0.4 Findings to discuss, in order of value

**(a) `--threshold` with one process makes false directional claims.** The gate is only as good as the interval under it. With `--processes 1`, between identical versions:

| | σ₂ = 1% | σ₂ = 2% |
|---|---|---|
| Simulation: "≥ 3%" claims | about 1% | **about 20%** |
| Pilot (real hardware) | 4% "slower ≥ 3%" | — |

With `--processes P > 1` the same gate gives at most 0.1%. *Suggestion:* when `--threshold > 0` and P = 1, warn, or report Inconclusive with a note to add `--processes`.

**(b) `--diff` across sessions can be badly wrong.** Simulating launch drift similar to the pilot's (0.1% per launch):

| | P = 10 | P = 20 |
|---|---|---|
| Versions interleaved | 97% coverage | 100% coverage |
| Separate sessions (what `--diff <ref>` does today) | **51%** | **0%** |

More processes make it worse, because the interval tightens around a biased estimate. *Suggestion:* §7.5, rebuild the ref and interleave both versions in one session. Building with different `-D` defines currently reuses one artifact path, so the two builds would need separate output directories.

**(c) `between_process_share` is inflated by correlated trials.** The first-difference within-process estimate removes slow drift from the *within* term, but that drift still moves each process mean. So it gets counted as between-process variance:

| | Reported share | True share |
|---|---|---|
| Simulation, lag-1 correlation 0.6 | 70.6% | 50% |
| Simulation, lag-1 correlation 0.6, no real between-process variance | about 30% | 0% |

In the pilot the reported share was 56.8%, against 44% from a plain ANOVA. The intervals are unaffected, because Fieller uses the process means directly. *Suggestion:* report σ̂₁, σ̂₂ and k̂ from an estimator that allows for correlation (ours: a moment estimator with an AR(1) term), or reword the README's interpretation of the share.

**(d) One unstable process hides the whole comparison.** Warmup stability is AND-ed across processes when they are merged. One process failing warmup marks the benchmark unstable and the comparison Unresolved, and the JSON no longer says which process it was. *Suggestion:* keep per-process `is_stable` in `process_trials`, and flag or exclude that process rather than dropping the comparison.

**(e) Spikes cost a lot of power with per-process means.** With 5% of trials hit by +30% spikes, power at θ = 1.05 with P = 5 falls from 71% to 22%. Coverage holds. A per-process **median** option would help. Whether pauses (GC, deoptimisation) count as part of the cost is a product decision (§8).

**(f) Defaults.** Out of the box users still get the single-process interval: 37% coverage at σ₂ = 1% in simulation, 57% false "excludes 1" on the pilot. Worth discussing: a higher `--processes` default for `--diff` and whenever `--threshold` is set, and when `--threshold` should become the default (§7.3 suggested δ = 5% for continuity).

### 0.5 Next on our side

- **Real-hardware validation (§5.2)** on several benchmarks: A/A, a calibrated +5% known effect, a same-binary `Benchmark.compare` group, and a different-day repeat.
- **A git-ref runner** (build both refs, interleave), as a prototype for (b).
- A **"Results on real hardware"** section here once those runs exist, mapping each piece of our tooling to a concrete bench_press change.

A Bayesian extension (borrowing σ₂ from history to make P = 3–5 usable) is planned after that. It will be proposed only if it beats the frequentist alternatives in the same validation.

## 1. Summary

bench_press already handles the hard engineering parts: dead-code-elimination barriers, adaptive warmup, ~100 ms batches, ABBA/BAAB interleaving and a Fieller ratio interval. This proposal adds four statistical pieces on top:

| # | Contribution | Problem it solves | Headline evidence |
|---|---|---|---|
| 1 | **Use the process as the unit of analysis** | The current 95% interval comes from batches inside one process. It ignores variation *between* processes, so it is too narrow. | With 1% batch noise and 0.5–1% process-to-process variation, the printed "95%" interval covers the truth only 39–65% of the time, and it excludes 1.00× in 35–61% of comparisons between identical binaries, so the interval column people read is misleading. Today's ±5% point band keeps the *verdict* quiet at that level (≈0% false Faster/Regression), but the protection fades as σ₂ grows: 8–10% false verdicts at σ₂ = 2% (E1). With 5–10 processes per version, the interval covers 95%. |
| 2 | **A practical-significance gate** | Today's verdict is "interval excludes 1.00× **and** point estimate past ±5%". A band on the point estimate ignores uncertainty. A real +5% change is called Faster only half the time however much data there is, real 2–3% changes get the same Neutral label as "no evidence", and nothing can confirm "no change". | At a true +5%, today's verdict says Faster 50% of the time. At +2–3% it says Faster 2–9% of the time and otherwise Neutral (E3). With P = 10, the gate detects +5% 98% of the time, never calls +1–2% meaningful, and reports "no meaningful change" 95% of the time when nothing changed. |
| 3 | **Validation of the method itself** | A "95%" label is a claim, and no test currently checks it. | A simulation harness plus an A/A protocol on real hardware report coverage, false-alarm rate and power. |
| 4 | **Experiment design** | How many processes, and how many batches each? | Per-level variance estimates give the cost-optimal split (Kalibera & Jones) and the processes needed for a target precision or power. |

The fix reuses `FiellerInterval.compute` unchanged. Only its inputs change: per-process means instead of per-batch means.

## 2. What bench_press does today (statistically)

- Each benchmark × target × matrix coordinate runs in **one process** (`run_command.dart`, `_executeFileCoordinates`).
- Within that process it records `trials` batch means (default 15; each batch is ~100 ms of calls).
- The delta verdict (`markdown_reporter.dart`, `_computeFiellerVerdict`) calls `FiellerInterval.compute(sampleA: base.rawTrialsNs, sampleB: cur.rawTrialsNs)`. Its inputs are the batch means of one baseline process and one candidate process. It uses Welch–Satterthwaite df and estimates $R=\bar x_A/\bar x_B$, so values above 1 mean the candidate is faster.
- The verdict combines `_computeFiellerVerdict` with `_classifyMovement` (both in `markdown_reporter.dart`):

  | Verdict | Condition |
  |---|---|
  | ❓ Unresolved | either side fails `isStable`, or Fieller's $g\ge1$ |
  | 🚀 Faster | the 95% interval excludes 1.00× **and** the point speedup is ≥ 1.05 |
  | ⚠️ Regression | the 95% interval excludes 1.00× **and** the point speedup is ≤ 0.95 |
  | ➖ Neutral | everything else: the interval contains 1.00×, **or** it excludes 1.00× but the point estimate is within (0.95, 1.05) |

  Two details matter below. Neutral merges "no evidence of a change" with "a detectable change smaller than 5%". The band is very slightly asymmetric: the slower bound is 0.95, not 1/1.05 ≈ 0.952.
- `--diff <git-ref>` loads a **previously saved** results JSON from that ref and compares it with a fresh run. The two sides come from different sessions.

Fieller's formula is implemented correctly. There are two separate issues: the **sampling unit** it is applied to (§3), and the **point-estimate band** used for the verdict (§4).

## 3. Contribution 1: the process as the unit of analysis

### 3.1 Model

Timing variation is nested (Kalibera & Jones 2013). For version $v$, process $p$ and batch $j$:

$$
x_{vpj} = \mu_v \,\alpha_{vp}\,(1+\varepsilon_{vpj}),\qquad
\log\alpha_{vp}\sim N(0,\sigma_2^2),\quad \varepsilon_{vpj}\sim N(0,\sigma_1^2)
$$

- $\sigma_1$ is **within-process** batch-to-batch noise: GC, scheduling, frequency changes.
- $\sigma_2$ is the **between-process** effect. Each fresh process gets its own memory layout (ASLR), initial heap, code placement and so on, and stays at that level for its whole life.

A third level, between builds or sessions, sits above these. It matters for `--diff` against a stored JSON (§3.5).

### 3.2 Why the current interval is too narrow

For one process with $n$ batches, the true variance of the version mean is $\mu_v^2(\sigma_2^2 + \sigma_1^2/n)$, but bench_press estimates only $\mu_v^2\,\sigma_1^2/n$.

The between-process term $\sigma_2^2$ is invisible from inside one process and doesn't shrink with $n$. The reported standard error is too small by the factor

$$
k=\sqrt{1+n\,\sigma_2^2/\sigma_1^2}
$$

(the *design effect* of survey sampling; $\sigma_2^2/(\sigma_1^2+\sigma_2^2)$ is the intraclass correlation). So the nominal 95% interval actually covers about

$$
\text{coverage}\approx 2\,\Phi(1.96/k)-1 .
$$

Two consequences run against intuition:
- **Better batching makes it worse.** bench_press's long 100 ms batches make $\sigma_1$ small, which makes $k$ large.
- **More trials make it worse.** $k$ grows with $n$, so the interval narrows around the process's own offset $\alpha_p$ rather than the true $\mu$ (§6, E2).

The ±5% point band (§2) partly shields the *verdict* from this. Between identical binaries, the point estimate rarely moves 5% when σ₂ ≤ 1%, so false Faster/Regression verdicts stay near 0% (E1, E2). The band does not fix the printed interval, which is still too narrow and is what readers use to judge precision. The protection also fades as σ₂ grows: at σ₂ = 2%, 8–10% of identical-binary comparisons get a Faster or Regression verdict (E1). How large σ₂ actually is on real hardware is what the A/A protocol (§5.2) measures.

### 3.3 The fix

1. Run $P$ fresh processes per version, interleaving baseline and candidate launches in random order.
2. Reduce each process to its mean, $\bar x_{vp}$.
3. Apply the existing `FiellerInterval.compute` to the $P$ baseline means against the $P$ candidate means.

Process means are independent, and each one's variance already includes both $\sigma_2^2$ and $\sigma_1^2/n$, so the interval is valid **without estimating either component**. The analysis assumes only that processes are independent. Autocorrelation, drift or non-normal noise *within* a process does not bias it, because none of that crosses process boundaries.

Required: $P\ge2$ per version. Recommended: $P\ge5$, and $P\ge10$ when using the bootstrap (§6, E5).

### 3.4 Variance components as a diagnostic

The same data gives per-level estimates through a one-way random-effects ANOVA on $y=\log x$ (log scale, because effects are multiplicative):

$$
\hat\sigma_1^2=\text{MS}_\text{within},\qquad
\hat\sigma_2^2=\max\!\Big(0,\ \tfrac{\text{MS}_\text{between}-\text{MS}_\text{within}}{n}\Big),\qquad
\hat k=\sqrt{1+n\hat\sigma_2^2/\hat\sigma_1^2}.
$$

Reporting $\hat\sigma_1$, $\hat\sigma_2$ and $\hat k$ per benchmark shows how much a single-process interval would have been overconfident. These estimates also drive experiment design (§5).

### 3.5 Same-binary comparisons and `--diff`

- **`Benchmark.compare` / groups (variants in one binary).** A process effect *shared* by all variants cancels in the ratio, which is a real advantage of in-binary interleaving. Effects *specific* to a variant (where its code lands, and how its allocation pattern interacts with the layout) do not cancel. How much remains is an empirical question, and the A/A protocol in §5.2 measures it directly.
- **Comparing two builds or git refs.** Different binaries get independent layouts, so the full $\sigma_2$ applies.
- **`--diff` against a stored JSON.** This adds a between-session term on top: machine state, thermal conditions, background load, possibly a different host. One process on each side cannot separate any of that from the code change. The statistically sound version builds both refs and runs their processes interleaved in the same session.

## 4. Contribution 2: the practical-significance gate

### 4.1 Rule

Given the ratio interval $[L,U]$ ($>1$ = faster) and a threshold $\delta$, using a band that is symmetric on the log scale:

| Verdict | Condition | Meaning |
|---|---|---|
| **Faster ≥ δ** | $L > 1+\delta$ | Confidently at least δ faster |
| **Slower ≥ δ** | $U < 1/(1+\delta)$ | Confidently at least δ slower |
| **No meaningful change** | $1/(1+\delta) < L$ and $U < 1+\delta$ | Any change is confidently smaller than δ. Optional sub-label: "detectable but < δ" when the interval excludes 1. |
| **Inconclusive** | otherwise | Not enough precision to decide relative to δ |

**Compared with today's rule.** bench_press already has a practical threshold: the ±5% band in `_classifyMovement`. The difference is *what* has to clear it:

| | Today (`_classifyMovement`) | Gate |
|---|---|---|
| Faster | interval excludes 1 **and** point estimate ≥ 1.05 | whole interval > 1+δ |
| "No change" | Neutral: interval contains 1, **or** point estimate within ±5% | interval inside ±δ (positive evidence) |
| Small real change | Neutral (same label as no change) | "no meaningful change, detectable but < δ" |
| Not enough data | Neutral (same label as no change) | Inconclusive |
| Uncertainty in the threshold decision | ignored: a point estimate of 1.051 with interval [1.01, 1.09] is Faster | required: the whole interval must clear δ |

**Choosing δ.** δ is a product decision about what size of change is worth acting on. The simulations use δ = 3%, the threshold our team picked. For bench_press, defaulting to δ = 5% keeps continuity with the existing band, with δ configurable per suite.

### 4.2 Why it matters statistically

- **A band on the point estimate ignores uncertainty.** At a true change of exactly 5%, the point estimate lands above 1.05 about half the time *regardless of sample size*. Today's verdict has ~50% power at its own threshold, and more data does not improve that (E3). The gate's error at the boundary is controlled by the interval instead: at most 2.5% per side, by construction.
- **It separates "no change" from "can't tell".** Today, Neutral covers no change, a real but sub-5% change, and too little data. The gate reports these separately.
- **It can positively confirm that nothing meaningful changed.** "The interval contains 1.00×" is only *absence of evidence*. "The interval lies inside ±δ" is *evidence of absence*. This is the two one-sided tests (TOST) equivalence logic. A 95% interval inside the band corresponds to TOST at α = 2.5% per side; a 90% interval would give the conventional α = 5%.
- **"Inconclusive" is informative.** It says precisely that more processes are needed, and §5 says how many.
- **It needs valid intervals underneath.** A gate on top of the one-process interval inherits its overconfidence, which is why contributions 1 and 2 go together.

### 4.3 Many benchmarks at once

This is a forward-looking concern, not a problem with today's verdicts. In a 20-benchmark suite of identical binaries, today's ±5% band produces about 0 false Faster/Regression verdicts per run at σ₂ ≤ 1%, and about 1.6 at σ₂ = 2%. The printed interval, however, excludes 1.00× in 7–16 of the 20 rows (§6, E7).

With valid intervals and the gate, a false "≥ δ" claim when nothing changed is very rare (≈0% in E3). It is bounded by 2.5% per benchmark only at the boundary θ = 1+δ. Multiplicity becomes a real issue in two cases:
- **Reporting the "detectable but < δ" sub-label**, or any "interval excludes 1" flag. These are tested at 5% per benchmark, so about one false flag per 20-benchmark run is expected.
- **Suites where many true effects sit just below δ.** Each of those carries up to 2.5% risk of a false "≥ δ" claim.

Options to discuss:
- report the expected number of false flags alongside the results;
- control the false discovery rate (Benjamini–Hochberg) across the table;
- automatically rerun flagged rows as a confirmation step.

## 5. Contributions 3 and 4: validation and experiment design

### 5.1 Validating the method (simulation)

The operating characteristics of the procedure, measured the way a clinical trial reports its error rates:

| Metric | Definition | Target |
|---|---|---|
| Coverage | P(interval contains the true θ) | ≈ 95% (Monte Carlo SE ±0.3 pp at 4,000 reps) |
| False-alarm rate | P(faster or slower verdict \| θ = 1) | ≈ 5% |
| False "meaningful" rate | P(faster ≥ δ \| 1 < θ < 1+δ) | ≤ 2.5% |
| Power | P(faster ≥ δ \| θ ≥ 1+δ+margin) | e.g. ≥ 80% at the planned P |
| Width | median interval width | reported, to compare estimators |

**Scenarios.** The baseline sweep is in [simulate.py](simulate.py). Robustness scenarios worth adding:
- heavy-tailed batch noise (Student t, lognormal spikes);
- within-process drift and autocorrelation;
- unequal variance between versions;
- a single outlier process;
- bimodal process effects ("good" and "bad" layouts).

**Estimators to compare:** current single-process Fieller; process-level Fieller; process-level bootstrap (percentile and BCa); a log-ratio Welch interval; and later a Bayesian hierarchical model.

### 5.2 Validating on real hardware: the A/A protocol

This is the most convincing test because it needs no model.

1. Build **one** AOT binary.
2. Launch it $2P$ times ($P$ = 15–20), randomly labelling each launch "A" or "B". Record every process's batch means.
3. **Empirical false-alarm rates:** pair A and B processes and apply today's single-process comparison to each pair. Count two things separately:
   - **how often the printed interval excludes 1.00×.** A calibrated interval does so about 5% of the time; E1 predicts 35–61% at σ₂ = 0.5–1%. With 15–20 pairs, 5% vs 35% is easy to tell apart.
   - **how often the verdict is Faster or Regression** (±5% band). E1 predicts ≈0% unless σ₂ approaches 2%, so a non-zero rate is itself evidence of large process-to-process variation.
4. **Variance components:** compute $\hat\sigma_1,\hat\sigma_2,\hat k$ (§3.4) on that machine for that benchmark.
5. **Same-binary variant:** repeat with a `Benchmark.compare` group whose candidate is an identical copy of the baseline. This measures how much of $\sigma_2$ cancels when variants share a binary (§3.5).
6. **Known-effect check:** add a calibrated extra cost to the candidate, such as a fixed spin loop worth ~5% of the iteration time. Then check that the interval contains the injected θ and that the gate fires.

The estimates from steps 4 and 6 also calibrate the simulation, closing the loop between §5.1 and real data.

### 5.3 Experiment design: how many processes, how many batches

On the log-ratio scale, with $P$ processes per version and $n$ batches per process:

$$
\operatorname{Var}(\log\hat\theta)\approx 2\left(\frac{\sigma_2^2}{P}+\frac{\sigma_1^2}{P\,n}\right).
$$

With $c_1$ the cost of a batch (~0.1 s) and $c_2$ the per-process overhead (startup, warmup, calibration), the total cost is $2P(c_2+n\,c_1)$. Minimising the variance for a fixed budget gives the Kalibera & Jones (2013) optimum:

$$
n^{\ast} = \sqrt{\frac{c_2}{c_1}\cdot\frac{\sigma_1^2}{\sigma_2^2}} .
$$

For a target 95% half-width $h$ on the log scale:

$$
P \approx \frac{2\cdot1.96^2\,(\sigma_2^2+\sigma_1^2/n)}{h^2}.
$$

The rule of thumb that follows: **when processes differ more than batches do, run more short processes rather than one long one.** $c_1$ is fixed by design (~100 ms), $c_2$ is easy to time from the runner, and §3.4 supplies $\sigma_1,\sigma_2$. So the tool could recommend $(P, n)$ itself after a pilot run. It could also stop adaptively once the interval is decisive relative to δ.

|---|---|---|---|---|---|---|---|
| 1.00 | 0% | 5% | 0% | 95% | 5% | 0% | 0% |
| 1.01 | 0% | 53% | 0% | 47% | 51% | 2% | 0% |
| 1.02 | 2% | 98% | 0% | 2% | 50% | 49% | 0% |
| 1.03 | 9% | 100% | 3% | 0% | 2% | 95% | 0% |
| 1.05 | 50% | 100% | 98% | 0% | 0% | 2% | 0% |
| 1.10 | 100% | 100% | 100% | 0% | 0% | 0% | 0% |

- **Today's verdict** has about 50% power at its own 5% threshold. That comes from the point-estimate band, not from sample size: more data would not raise it. Real 2–3% changes are almost always Neutral, the same label as "no change". *Caveat:* the "today" column uses 1 process per version and the gate columns use 10, so this column shows the behaviour of the rule, not a cost-matched comparison.
- **"P=10: interval excludes 1"** shows what a bare "interval excludes 1" rule would do with valid intervals: it flags 98% of +2% changes. A significance test alone is not a practical threshold.
- **The gate:**
  - **Below δ (θ = 1.01–1.02):** it never claims a meaningful speedup.
  - **At δ (θ = 1.03):** it is honestly inconclusive, and the 3% "faster" rate is the designed error rate at the boundary.
  - **Above δ (θ = 1.05):** it detects the speedup 98% of the time.

### E5. Choice of estimator: process-level Fieller vs percentile bootstrap (θ = 1)

| P per version | Fieller cov. | bootstrap cov. | Fieller median width | bootstrap median width |
|---|---|---|---|---|
| 3 | 96% | 80% | 4.85% | 2.38% |
| 5 | 96% | 88% | 3.02% | 2.16% |
| 10 | 96% | 92% | 1.94% | 1.69% |
| 20 | 95% | 94% | 1.31% | 1.23% |

With few processes the percentile bootstrap is overconfident, because it cannot see variability beyond the handful of processes it resamples. Fieller's *t*-based interval is the safer default at small P. The bootstrap becomes competitive at P ≈ 20, where it is useful for skewed or outlier-prone process means.

## 7. Suggested changes to bench_press

These are listed in order of statistical value and are open for discussion; none is required in a particular form.

1. **`--processes N`**: run each benchmark × target × coordinate in N fresh processes. When comparing versions, interleave their launches in random order. Store per-process results in the JSON schema (for example, a list of runs, each with its `raw_trials_ns`). With N = 1, behaviour is unchanged, but the report notes that between-process variance was not measured.
2. **Process-level Fieller** in `_computeFiellerVerdict`, with per-process means as inputs. The existing `FiellerInterval.compute` is reused as-is.
3. **`--threshold δ`** to switch on the four-way verdict of §4.1. It would replace the ±5% point band in `_classifyMovement`, or sit alongside it during a transition. Defaulting to δ = 5% keeps today's threshold while moving the decision from the point estimate to the interval.
4. **Diagnostics:** report $\hat\sigma_1$, $\hat\sigma_2$ and $\hat k$ per benchmark, plus a warning when $\hat k$ is large.
5. **`--diff <git-ref>` that rebuilds** the reference and runs both versions interleaved in the same session, instead of only reading a stored JSON.
6. **Later:** $(P, n)$ recommendations from a pilot run (§5.3), multiple-comparison control (§4.3), and adaptive stopping relative to δ.

## 8. Assumptions and limitations

- **The σ₂ values are scenarios, not measurements.** How large process-to-process variation is for Dart AOT on a given machine is the key unknown, and the A/A protocol in §5.2 is designed to measure it. If σ₂ turns out to be ≈ 0 for a benchmark, today's interval is already fine for it, and the diagnostic in §3.4 would show that.
- **The simulation model is simple:** normal, independent batches and a lognormal process effect. The robustness scenarios in §5.1 are there to test that.
- **Interval semantics:** Fieller here targets the **ratio of mean** batch times. Whether mean or median time is the right target depends on whether occasional pauses (GC, deoptimisation) count as part of the cost. That is a product decision, not a statistical one.
- **Small P:** with P < 5 the intervals are valid but wide (E4, E5). That is the honest price of not knowing σ₂.
- **Comparisons with "today"** use bench_press's actual verdict rule at `e21db31`, including the ±5% point band in `_classifyMovement`. The `isStable` gate is not modelled; at these σ₁ values the CV is well under its 5% limit.
